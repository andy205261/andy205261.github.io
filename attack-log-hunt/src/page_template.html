Ransomware Precursor Hunt

Before ransomware encrypts a hospital's files, the attacker runs hidden PowerShell, plants a scheduled task, deletes the backups and turns off antivirus. I wrote five Sigma detections for those steps, tuned them on one set of real attack logs, then tested them on a second set I had not looked at.

SigmapySigma → SQLPythonWindows event logsSysmonMITRE ATT&CKThreat hunting

Public data only. Both datasets are published attack recordings from security researchers' lab machines. No patient data, no employer data, nothing installed. The raw logs are downloaded by the script, not stored here, and URLs from attacks are defanged (hxxps).

Why this matters

When ransomware hits a hospital, clinicians switch to paper and downtime procedures, sometimes for weeks. The encryption is the last step. Hours or days earlier, the attacker runs a short list of very recognizable commands to stay in, hide, and make recovery impossible. Catching those commands is the window where a SOC can still isolate one machine instead of restoring a whole hospital.

How it works

ParseEvery EVTX file is read; process starts (Sysmon 1, Security 4688) go into one table.
DetectEach Sigma rule is converted to SQL with pySigma and run against that table.
Hunt and labelLoose keyword hunts pull every possible candidate. Each one is labelled by hand before scoring.
ScoreCaught, missed and false hits per rule, per dataset, per version.

The unit is one unique attack action (log file + command line). A cmd.exe /c wrapper or net.exe → net1.exe pair is the same action seen twice, so it is not counted as a separate miss, and an alert on it is counted as a repeat, not a false hit.

Limits

  • Zero false hits is not a hospital number. Both datasets are attack recordings from lab machines, not a normal workday of clinical workstations, so they cannot show how noisy these rules would be at a real site. The next test is a benign baseline: a week of normal endpoint logs.
  • Small numbers. {{DEV_N}} and {{HO_N}} in-scope actions are enough to find blind spots, not to quote a detection rate with confidence.
  • One labeller. I labelled every candidate myself. The labels, with a reason for each, are in src/label.py and labels/ground_truth.csv so anyone can disagree with a specific call.
  • Command lines only. The rules see process starts. Script content, registry, network and Defender's own events would catch much of what was missed.

Next (v3 backlog)

  • D1: move hidden-PowerShell detection to Script Block Logging (Event 4104); keep the command-line rule as a cheap first signal.
  • D4: cover the behaviour across tools (WMIC shadowcopy delete, wbadmin delete backup, PowerShell Win32_ShadowCopy).
  • D5: add Defender operational events 5001 and 5007, plus sc config WinDefend.
  • D2: alert once per action (skip net1.exe when its parent is net.exe).
  • Score v3 on a third dataset, not on either of these two.
