# EHR Access Monitoring

Detecting insider snooping in hospital EHR audit logs: who opened a patient's chart without a reason to.

SQL rules check every chart access against care-team assignments, encounters and job roles, flag suspicious patterns, and roll them up into a ranked investigation queue for a privacy analyst. The rules are measured against labeled misuse, then tuned.

> **All data is synthetic.** "Riverside General Hospital", its staff and its patients are fictional and generated by `src/generate_data.py`. No real PHI, no real organization, no employer data.

## Results

| | v1 baseline | v2 tuned |
|---|---|---|
| Users wrongly flagged | 21 | 2 |
| Misusers caught (of 36) | 34 | 35 |
| Event precision | 80.5% | 96.6% |
| Event recall | 89.0% | 99.1% |
| Real misusers in top 20 of queue | 19 | 20 |

Dataset: 39,936 chart accesses over 30 days, 280 staff, 2,470 patients, 2,303 encounters. 227 planted misuse events by 36 users across 10 scenarios.

**v1** used only the core clinical tables. Its false alerts were legitimate work it couldn't see: an approved quality audit, staff picking up extra shifts, after-hours claim rework, and specialist consults.
**v2** adds three context sources hospitals already have (consult orders, approved work queues, staffing schedules) and two behavioral rules for misuse v1 missed (low-and-slow browsing, excessive access by a care-team member).

## Rules

| ID | Rule | Weight |
|---|---|---|
| R1 | VIP record, no relationship | 30 |
| R2 | Family record (same last name and address), no relationship | 35 |
| R3 | Coworker record, no relationship | 25 |
| R4 | Break-the-glass without an active emergency in the user's unit | 30 |
| R5 | 15+ distinct unrelated patients in one day | 40 |
| R6 | Account used after termination | 50 |
| R7 | Off-shift access to an unrelated record | 10 |
| R8 (v2) | 8+ distinct unrelated patients over the period, below the daily R5 limit | 25 |
| R9 (v2) | Care-team member opens a VIP or staff record 10+ times and 2.5x their peers | 20 |

A user's risk score is the sum of the weights of the rules they triggered plus 2 points per flagged event (capped at 20 events).

## Misuse scenarios planted

VIP snooping · family record snooping · coworker snooping · break-the-glass misuse · bulk browsing · access after termination · after-hours access · low-and-slow browsing · excessive access by a care-team member · curiosity break-the-glass on a coworker's live ED visit.

The data also contains legitimate work designed to look suspicious (consults, audits, extra shifts, after-hours billing, float coverage), so precision is a real test.

## Known gaps

- **Curiosity inside a real emergency.** Break-the-glass on a coworker's active ED visit looks justified, so v2 misses it. Fix: always review break-the-glass on staff and VIP records.
- **R9 flags the whole pattern**, including the user's routine opens. Correct at user level; noisy at event level.
- **Float coverage with no recorded assignment** still looks like snooping. That's a data-quality fix at the source.
- **Thresholds fit this dataset.** A real deployment would baseline by role and unit first.

## HIPAA Security Rule mapping

| Requirement | Where |
|---|---|
| Audit controls, 45 CFR 164.312(b) | Access log captured and analyzed |
| Information system activity review, 164.308(a)(1)(ii)(D) | Ranked investigation queue |
| Information access management, 164.308(a)(4); minimum necessary, 164.502(b) | Relationship check, R1–R3, R5, R8, R9 |
| Emergency access procedure, 164.312(a)(2)(ii) | R4 |
| Termination procedures, 164.308(a)(3)(ii)(C) | R6 |

## Run it

```bash
pip install pandas
python src/generate_data.py   # synthetic hospital + labeled misuse  -> data/
python src/run_detection.py   # v1 and v2 rules, scored             -> output/
python src/build_page.py      # results page                        -> index.html
```

Everything is seeded, so results are reproducible.

## Repo layout

```
data/            synthetic tables (users, patients, encounters, care_team,
                 consult_orders, work_queue, extra_shifts, access_log)
sql/             v1_baseline.sql, v2_tuned.sql
src/             generate_data.py, run_detection.py, build_page.py
output/          alerts_v*.csv, user_risk_v*.csv, metrics.json
index.html       portfolio results page
```

Ground-truth columns (`is_anomaly`, `scenario`, `context`) are dropped before the data reaches SQLite; they are joined back only when scoring.
